# 2.13 - Finance MVP

## Overview
Finance MVP introduces monthly tuition plans, student billing, and cash payment tracking for Quran centers in Yemen.

- Stack: MySQL + Prisma + Express + React
- Backend path: `backend/src/modules/finance`
- Frontend path: `frontend/src/features/finance`, `frontend/src/pages/FinancePage.tsx`
- Router prefix: `/finance`

## ERD

```text
organizations (1) ---- (N) tuition_plans
centers       (1) ---- (N) tuition_plans

users (student)      (1) ---- (N) student_tuition_assignments
tuition_plans        (1) ---- (N) student_tuition_assignments

users (student)      (1) ---- (N) invoices
centers              (1) ---- (N) invoices

invoices             (1) ---- (N) payments
users (received_by)  (1) ---- (N) payments
```

## Prisma Models

### `tuition_plans`
- `id` PK
- `organizationId` FK -> `organizations.id`
- `centerId` FK -> `centers.id`
- `name`
- `monthlyAmount` (`Decimal(10,2)`)
- `isActive` (`Boolean`, default `true`)
- `createdAt`
- Unique: `(centerId, name)`

### `student_tuition_assignments`
- `id` PK
- `studentId` FK -> `users.id`
- `tuitionPlanId` FK -> `tuition_plans.id`
- `startDate`
- `endDate` nullable
- `status` (`ACTIVE | INACTIVE`)
- Unique: `(studentId, tuitionPlanId)`

### `invoices`
- `id` PK
- `studentId` FK -> `users.id`
- `centerId` FK -> `centers.id`
- `month` (`1..12`)
- `year`
- `amount` (`Decimal(10,2)`)
- `status` (`PENDING | PARTIAL | PAID`)
- `issuedAt`
- `createdAt`
- Unique: `(studentId, month, year)`
- Index: `(centerId, year, month)`

### `payments`
- `id` PK
- `invoiceId` FK -> `invoices.id`
- `amount` (`Decimal(10,2)`)
- `method` (`CASH | TRANSFER`)
- `receivedById` FK -> `users.id`
- `receivedAt`
- `createdAt`

## Business Rules

1. Monthly subscription model per center via `tuition_plans`.
2. Payment methods are controlled (`CASH`, `TRANSFER`), with cash as default.
3. Payment cannot exceed remaining invoice balance.
4. Invoice status is auto-updated:
   - `totalPaid == amount` -> `PAID`
   - `0 < totalPaid < amount` -> `PARTIAL`
   - `totalPaid == 0` -> `PENDING`
5. Parent can only see invoices tied to their children.
6. Teacher has no finance API access.
7. Center Admin is restricted to server-side center scope.
8. Super Admin has organization-wide view.
9. Deletion rule enforced in domain: paid invoices must not be deleted.

## Sample API Calls

### Login
```bash
curl -X POST http://localhost:4000/auth/login \
  -H "Content-Type: application/json" \
```

```bash
curl "http://localhost:4000/finance/invoices?month=2&year=2026" \
```

```bash
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
```

```bash
curl -X POST http://localhost:4000/finance/payments \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"invoiceId":22,"amount":2500,"method":"CASH"}'
```

## Scoping Enforcement

Server-side scope resolution is reused from shared middleware:

1. `authGuard` resolves authenticated user.
2. `attachScope` resolves `organizationId`, `centerIds`, `studentIds`.
3. `requireRoles` blocks unauthorized roles before service logic.
4. Finance service/domain enforces:
   - center visibility checks for admin flows
   - parent visibility checks by `studentIds`
   - invoice-level visibility checks before reading payments/details

No client-side storage-based scope is trusted.

## Seed Logic (Idempotent Behavior)

Finance seed extension creates:

1. One tuition plan per center.
2. Student-to-plan assignments.
3. Four invoices (current + previous month across 2 students).
4. One partial payment on current month north-center invoice.
5. Status normalization pass (PENDING/PARTIAL/PAID) based on actual payment sums.

Repeated seed execution preserves stable counts and avoids duplication in finance entities.
