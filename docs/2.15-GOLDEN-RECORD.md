# 2.15 - Golden Record (السجل الذهبي)

## 1) Overview

Golden Record is a new **web-only** admin module inside the existing Rafiq Al-Quran dashboard. It is not a standalone product and must follow the current platform conventions already present in the codebase:

- Multi-tenant SaaS, scoped by `organization_id`
- Admin dashboard only
- Allowed roles: `SUPER_ADMIN`, `CENTER_ADMIN`
- Sidebar is the primary navigation
- No breadcrumb by default
- Page-level actions use the existing `PageHeader`
- Detail interactions happen in modals, not separate detail pages
- Arabic RTL first

### Recommended placement in the current dashboard

- Sidebar section: `operations`
- Sidebar route id: `golden_records`
- Sidebar label: `السجل الذهبي`
- Base route: `/golden-records`

### Recommended page structure

Use **one sidebar item** with **three internal page tabs/views** under the same module shell:

1. `/golden-records/candidates`
2. `/golden-records/statistics`
3. `/golden-records/final`

This keeps the sidebar clean and matches the current Exams module pattern while still giving the product the three required pages.

## 2) Module Goals

The module has five operational goals:

1. Maintain the yearly operational list of students expected to graduate.
2. Record Quran completion and final khatma/ijazah exam evidence.
3. Maintain the official final graduation registry.
4. Provide center-level and organization-level year-end achievement statistics.
5. Serve as a printable/exportable official registry for approved graduates.

The module is not for teachers, supervisors, students, or parents. It is strictly an admin registry and approval workflow.

## 3) Roles & Permissions

### Access policy

- Only `SUPER_ADMIN` and `CENTER_ADMIN` can access the module.
- All other roles receive `403 Forbidden` and should not see the sidebar item.
- Backend scoping must reuse the existing `authGuard + attachScope + verifyScope` pattern.

### Permission matrix

| Capability | SUPER_ADMIN | CENTER_ADMIN |
|---|---|---|
| View candidates | All centers | Own center only |
| Create candidates | Yes | Yes |
| Edit candidates before approval | Yes | Yes, own center only |
| Move candidate to `SCHEDULED` / `TESTED` | Yes | Yes, own center only |
| Approve candidate | Yes | No |
| Reject candidate | Yes | No |
| Defer candidate | Yes | No |
| View statistics | Organization + all centers | Own center only |
| Create final record manually | Yes | Yes, own center only |
| Create final record from approved candidate | Yes | Yes, own center only |
| Edit final record before approval | Yes | Yes, own center only |
| Submit final record for approval | Yes | Yes |
| Approve final record | Yes | No |
| Reject final record | Yes | No |
| Export / print approved records | Yes | Yes, own center only |

### Scoping rules

- `SUPER_ADMIN`
  - `allAccess = true`
  - can query any center
  - can view organization aggregate statistics
- `CENTER_ADMIN`
  - `centerIds` limited to assigned center(s) through the current scope system
  - every query and mutation must be validated against scope
  - center selector in UI is hidden or locked to the admin's own center

## 4) Data Model

### Core entities

1. `graduation_candidates`
   - Operational workflow entity for the current or selected year
   - Tracks nomination, scheduling, testing, and approval decision
   - Linked to student, center, halaqa, and optional exam/attempt

2. `golden_records`
   - Official registry entity
   - Created manually or from an approved candidate
   - Becomes legally/administratively final only after Super Admin approval

3. `student_yearly_achievement_snapshots`
   - Historical yearly snapshot per student
   - Required for correct year-over-year statistics
   - Prevents old statistics from changing when `student_profiles.current_juzz` changes later

### Existing entities reused from the current system

- `users`
  - student is a `User` with role `STUDENT`
- `student_profiles`
  - reuse `current_juzz`
  - recommended to update `studentStatus = GRADUATED` only after final Golden Record approval
- `centers`
- `circles`
- `exams`
- `exam_attempts`
- `audit_logs`
- `report_runs` / `report_files` for export reuse

### Relationship map

```text
organizations (1) ---- (N) graduation_candidates
organizations (1) ---- (N) golden_records
organizations (1) ---- (N) student_yearly_achievement_snapshots

centers (1) ---- (N) graduation_candidates
centers (1) ---- (N) golden_records
centers (1) ---- (N) student_yearly_achievement_snapshots

circles (1) ---- (N) graduation_candidates
circles (1) ---- (N) golden_records (optional link)
circles (1) ---- (N) student_yearly_achievement_snapshots (optional link)

users[STUDENT] (1) ---- (N) graduation_candidates
users[STUDENT] (1) ---- (N) golden_records
users[STUDENT] (1) ---- (N) student_yearly_achievement_snapshots

graduation_candidates (1) ---- (0..1) golden_records
exam_attempts (1) ---- (0..1) graduation_candidates
exam_attempts (1) ---- (0..1) golden_records
```

### Snapshot strategy

Official records must not drift when names change later. For that reason:

- `golden_records` stores:
  - `student_name_snapshot`
  - `center_name_snapshot`
  - `circle_name_snapshot`
- `graduation_candidates` may also store snapshots for stable table/export behavior

Purpose: historical base table for year-end statistics.

### Why no `achievement_categories` table initially

Do **not** create an `achievement_categories` lookup table in v1. The categories are fixed, small, and code-driven. A dedicated table would add complexity without business value. Localization belongs in frontend labels, not configuration data.

## 6) Process Flow

### End-to-end lifecycle

```text
Student
-> Candidate nominated
-> Quran completion recorded
-> Khatma exam scheduled
-> Exam completed
-> Result entered
-> Candidate approved by Super Admin
-> Final Golden Record created
-> Final Golden Record approved by Super Admin
-> Included in official registry and yearly statistics
```

### Candidate lifecycle

| Current Status | Action | Performed By | Next Status | Validation |
|---|---|---|---|---|
| none | Create candidate | `SUPER_ADMIN`, `CENTER_ADMIN` | `NOMINATED` | Student must be in scope, one candidate per student/year |
| `NOMINATED` | Set exam date / link exam | `SUPER_ADMIN`, `CENTER_ADMIN` | `SCHEDULED` | `khatma_test_date` required |
| `DEFERRED` | Re-open and reschedule | `SUPER_ADMIN`, `CENTER_ADMIN` | `SCHEDULED` or `NOMINATED` | Same year only |
| `SCHEDULED` | Record exam result | `SUPER_ADMIN`, `CENTER_ADMIN` | `TESTED` | Exam evidence required |
| `TESTED` | Approve | `SUPER_ADMIN` | `APPROVED` | Grade/average or reviewed exam attempt required |
| `TESTED` | Reject | `SUPER_ADMIN` | `REJECTED` | Rejection reason required |
| `NOMINATED`, `SCHEDULED`, `TESTED` | Defer | `SUPER_ADMIN` | `DEFERRED` | Defer reason required |

Rules:

- `APPROVED` is terminal for the candidate workflow.
- `REJECTED` is terminal for the current year unless reopened through an explicit admin operation.
- `CENTER_ADMIN` cannot move a candidate to `APPROVED`, `REJECTED`, or `DEFERRED`.
- `TESTED` requires documented result evidence.

### Final record lifecycle

| Current Status | Action | Performed By | Next Status | Validation |
|---|---|---|---|---|
| none | Create record | `SUPER_ADMIN`, `CENTER_ADMIN` | `DRAFT` | Manual: exam data required. From candidate: candidate must be `APPROVED` |
| `DRAFT` | Edit | `SUPER_ADMIN`, `CENTER_ADMIN` | `DRAFT` | Scoped, not approved yet |
| `DRAFT` | Submit for approval | `SUPER_ADMIN`, `CENTER_ADMIN` | `SUBMITTED` | Required fields complete |
| `SUBMITTED` | Approve | `SUPER_ADMIN` | `APPROVED` | Unique check passes, serial generated |
| `SUBMITTED` | Reject | `SUPER_ADMIN` | `REJECTED` | Rejection note required |
| `REJECTED` | Revise | `SUPER_ADMIN`, `CENTER_ADMIN` | `DRAFT` | Rejection note preserved in audit |

On final approval the system must:

1. Generate `registry_serial`.
2. Lock the record against normal edits.
3. Write audit log entries.
4. Create or update `student_yearly_achievement_snapshots` for that student/year.
5. Recommended: set `student_profiles.student_status = GRADUATED`.

### Who performs each step

1. Candidate nomination: `CENTER_ADMIN` or `SUPER_ADMIN`
2. Memorization completion entry: `CENTER_ADMIN` or `SUPER_ADMIN`
3. Exam scheduling: `CENTER_ADMIN` or `SUPER_ADMIN`
4. Exam completion/result entry: `CENTER_ADMIN` or `SUPER_ADMIN`
5. Candidate approval/rejection/defer: `SUPER_ADMIN`
6. Final record creation: `CENTER_ADMIN` or `SUPER_ADMIN`
7. Final record approval: `SUPER_ADMIN`
8. Organization-level statistics review: `SUPER_ADMIN`
9. Center-level statistics review: `CENTER_ADMIN` or `SUPER_ADMIN`

## 7) Use Cases

### UC-1: Nominate a student for graduation

- Actor: `CENTER_ADMIN`
- Preconditions:
  - student belongs to accessible center
  - no existing candidate for the same student/year
- Result:
  - row added to `graduation_candidates` with status `NOMINATED`

### UC-2: Schedule the final khatma test

- Actor: `CENTER_ADMIN`
- Preconditions:
  - candidate is `NOMINATED` or `DEFERRED`
- Result:
  - `khatma_test_date` recorded
  - optional `exam_id` / `exam_attempt_id` linked
  - status becomes `SCHEDULED`

### UC-3: Record exam result

- Actor: `CENTER_ADMIN`
- Preconditions:
  - candidate is `SCHEDULED`
- Result:
  - grade/average snapshot or reviewed `exam_attempt_id` linked
  - status becomes `TESTED`

### UC-4: Approve or reject candidate

- Actor: `SUPER_ADMIN`
- Preconditions:
  - candidate is `TESTED`
- Result:
  - status becomes `APPROVED` or `REJECTED` or `DEFERRED`
  - audit log written

### UC-5: Create final record from approved candidate

- Actor: `CENTER_ADMIN`
- Preconditions:
  - candidate status is `APPROVED`
  - no final record already linked to that candidate
- Result:
  - `golden_records` row created in `DRAFT`
  - fields prefilled from candidate and exam

### UC-6: Create manual final record for legacy/imported graduate

- Actor: `SUPER_ADMIN` or `CENTER_ADMIN`
- Preconditions:
  - student belongs to scope
  - documented exam data available
- Result:
  - `golden_records` row created in `DRAFT` with `source = MANUAL`

### UC-7: Final approval of official record

- Actor: `SUPER_ADMIN`
- Preconditions:
  - record status is `SUBMITTED`
  - required fields complete
  - uniqueness constraint passes
- Result:
  - record becomes `APPROVED`
  - official registry serial generated
  - record becomes printable/exportable

### UC-8: View year-end statistics

- Actor: `SUPER_ADMIN` or `CENTER_ADMIN`
- Preconditions:
  - snapshot data exists for selected year
- Result:
  - cards and breakdown table show counts by category

### UC-9: Export registry

- Actor: `SUPER_ADMIN` or `CENTER_ADMIN`
- Preconditions:
  - user is within scope
  - filters valid
- Result:
  - PDF or XLSX generated through report/export infrastructure

## 8) Business Rules

1. Only `SUPER_ADMIN` and `CENTER_ADMIN` can access this module.
2. `CENTER_ADMIN` is strictly limited to accessible center IDs from current scope resolution.
3. Candidate uniqueness is per `student + year + organization`.
4. Final Golden Record uniqueness is per `student + year + type + organization`.
5. Candidate must be `APPROVED` before creating a final record from candidate flow.
6. Manual final record creation is allowed, but still requires documented exam data.
7. A Golden Record cannot be finally approved without `exam_date`, `grade`, `average`, and `appreciation`.
8. `riwaya` is mandatory when `type = IJAZAH`.
9. `riwaya` is optional and usually null when `type = KHATEM`.
10. Candidate status transitions are restricted to the lifecycle table above.
11. Final record status transitions are restricted to the lifecycle table above.
12. `CENTER_ADMIN` cannot approve, reject, or defer a candidate.
13. `CENTER_ADMIN` cannot approve a final Golden Record.
14. Approved final records are immutable except through a dedicated future reversal flow; regular PATCH must reject edits.
15. Statistics for previous years must come from snapshot data, not from current live `student_profiles.current_juzz`.
16. Approved Golden Records should contribute `JUZ_30` to yearly achievement statistics.
17. Export and print operate only on scoped data.
18. Every create, edit, submit, approve, reject, and export action must write to `audit_logs`.
19. No detail page should exist; all record inspection and actions happen in modals.
20. Default filters on candidates and statistics should open on the current Hijri/Gregorian business year used by the organization; if the system currently uses Gregorian `year`, keep it consistent everywhere.

- `إلغاء`

## 11) API Design

### Router structure

Recommended backend router prefix:

- `/golden-records`

### A. Candidates API

#### `GET /golden-records/candidates`

Query params:

- `year` required, default current year
- `centerId` optional, Super Admin only or scoped Center Admin center
- `circleId` optional
- `status` optional
- `search` optional
- `page` optional
- `pageSize` optional

Behavior:

- server-side scoped by `attachScope`
- `verifyScope("center", "query", "centerId")`
- if `circleId` exists, also verify circle scope

Response shape:

```json
{
  "items": [],
  "page": 1,
  "pageSize": 20,
  "total": 0,
  "summary": {
    "total": 0,
    "approved": 0,
    "deferred": 0,
    "pending": 0
  }
}
```

#### `POST /golden-records/candidates`

Body:

```json
{
  "studentId": 25,
  "year": 2026,
  "centerId": 3,
  "circleId": 9,
  "memorizationCompletionDate": "2026-06-10",
  "khatmaTestDate": null,
  "memorizationStartDate": "2023-09-01",
  "memorizationDurationMonths": 33,
  "notes": "مرشح للختمة النهائية"
}
```

Validation:

- student must exist and be role `STUDENT`
- candidate must be unique per student/year
- center/circle must be inside caller scope
- if `circleId` provided, it must belong to `centerId`

#### `PATCH /golden-records/candidates/:id`

Allowed for:

- `SUPER_ADMIN`
- `CENTER_ADMIN` before approval

Patchable fields:

- `circleId`
- `memorizationCompletionDate`
- `khatmaTestDate`
- `memorizationStartDate`
- `memorizationDurationMonths`
- `notes`
- `examId`
- `examAttemptId`
- `status` only for non-terminal operational states:
  - `NOMINATED`
  - `SCHEDULED`
  - `TESTED`

Validation:

- cannot patch candidate after final record already exists, except notes
- cannot set `status = TESTED` without exam evidence
- cannot move to `APPROVED`, `REJECTED`, or `DEFERRED` using generic PATCH

#### `POST /golden-records/candidates/:id/approve`

Body:

```json
{
  "note": "تمت المراجعة والاعتماد",
  "lockVersion": 2
}
```

Validation:

- only `SUPER_ADMIN`
- current status must be `TESTED`
- exam result must exist

Effect:

- candidate status becomes `APPROVED`

#### `POST /golden-records/candidates/:id/reject`

Body:

```json
{
  "reason": "نتيجة الاختبار لا تحقق شرط الاعتماد",
  "lockVersion": 2
}
```

Validation:

- only `SUPER_ADMIN`
- current status must be `TESTED`
- reason required

Effect:

- candidate status becomes `REJECTED`

#### Recommended supporting endpoint: `POST /golden-records/candidates/:id/defer`

Body:

```json
{
  "reason": "تأجيل إلى دورة لاحقة",
  "lockVersion": 2
}
```

Validation:

- only `SUPER_ADMIN`
- allowed from `NOMINATED`, `SCHEDULED`, `TESTED`

### B. Golden Records API

#### `GET /golden-records`

Query params:

- `year` optional
- `centerId` optional
- `type` optional
- `riwaya` optional
- `status` optional
- `search` optional
- `page` optional
- `pageSize` optional

Behavior:

- scoped by center
- default sort: newest approved first, then newest created

#### `POST /golden-records`

Body for candidate-based creation:

```json
{
  "source": "CANDIDATE",
  "candidateId": 44,
  "type": "KHATEM",
  "grade": "95/100",
  "average": 95,
  "appreciation": "ممتاز",
  "examDate": "2026-07-02",
  "notes": "اعتماد نهائي للختمة"
}
```

Body for manual creation:

```json
{
  "source": "MANUAL",
  "studentId": 25,
  "year": 2026,
  "centerId": 3,
  "circleId": 9,
  "type": "IJAZAH",
  "riwaya": "HAFS",
  "grade": "98/100",
  "average": 98,
  "appreciation": "ممتاز مع مرتبة الشرف",
  "examDate": "2026-07-02",
  "notes": "إدخال تاريخي"
}
```

Validation:

- `source = CANDIDATE`
  - candidate must be `APPROVED`
  - candidate must not already have a final record
- `source = MANUAL`
  - student must be in scope
  - exam data mandatory
- `riwaya` required for `IJAZAH`
- no duplicate `student + year + type`

#### `PATCH /golden-records/:id`

Patchable fields when status is `DRAFT` or `REJECTED`:

- `grade`
- `average`
- `appreciation`
- `examDate`
- `type`
- `riwaya`
- `notes`
- `status`

Status changes allowed by PATCH:

- `DRAFT -> SUBMITTED`
- `REJECTED -> DRAFT`

Blocked:

- editing `APPROVED`
- setting `APPROVED` by PATCH

#### `POST /golden-records/:id/approve`

Body:

```json
{
  "note": "تم الاعتماد النهائي",
  "lockVersion": 1
}
```

Validation:

- only `SUPER_ADMIN`
- status must be `SUBMITTED`
- all required fields complete
- unique constraints still pass

Effect:

- status becomes `APPROVED`
- `registry_serial` generated
- snapshot row upserted into `student_yearly_achievement_snapshots`

#### Recommended supporting endpoint: `POST /golden-records/:id/reject`

Body:

```json
{
  "reason": "البيانات غير مكتملة",
  "lockVersion": 1
}
```

Effect:

- status becomes `REJECTED`

#### Export / print endpoints

Recommended:

- `GET /golden-records/export?year=2026&centerId=3&type=KHATEM&format=xlsx`
- `GET /golden-records/:id/print`

Implementation note:

- reuse the existing `report_runs` / `report_files` infrastructure instead of inventing a parallel export system

## 13) Final Recommendations

1. Implement Golden Record as **one sidebar module with three internal views**, not three separate sidebar items.
2. Treat `golden_records` as the official legal/administrative registry and keep immutable snapshots there.
3. Introduce `student_yearly_achievement_snapshots` in v1; otherwise historical statistics will become unreliable.
4. Reuse the existing Exams module for exam evidence and the existing Reports infrastructure for export.
5. Update `student_profiles.student_status` to `GRADUATED` only after final Golden Record approval, not after candidate approval.
6. Keep all approval decisions server-enforced; do not rely on frontend-only hiding of actions.
7. Normalize Quran certification enums before implementation. The current codebase already contains `KhatmType` / `RiwayaType` usage, and this module should avoid introducing conflicting naming between backend and frontend.
